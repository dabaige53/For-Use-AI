# 一次 AI 对话的完整输入与输出：备课资料

核验日期：2026-09-15。选题聚焦带工具能力的对话系统：产品怎样组织模型输入，模型怎样生成回答或动作请求，外部执行结果怎样返回上下文。

## 推荐先读的三份材料

1. **[Effective context engineering for AI agents](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)**：建立完整上下文的概念，适合作为文章主线依据。
2. **[Explore the context window](https://code.claude.com/docs/en/context-window)**：用一个具体产品说明哪些信息预先加载、哪些动态加入，适合准备图解。
3. **[Define tools](https://platform.claude.com/docs/en/agents-and-tools/tool-use/define-tools)**：解释工具名称、描述、参数 Schema 如何被提供给模型，直接对应本课重点。

三份材料分别回答“整体是什么”“什么时候加入”“工具定义长什么样”。先读它们，再用下列材料补齐调用循环和实现差异。

## 核心资料及使用方法

### S1｜完整上下文的组成与维护

**Anthropic — [Effective context engineering for AI agents](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)**，2025-09-29，英文工程长文，难度中等。

重点阅读 *Context engineering vs. prompt engineering*、*The anatomy of effective context*、*Context retrieval and agentic search* 及长任务部分。文章讨论系统指令、工具、外部数据、消息历史，以及资料如何按需检索、摘要和重新组织。

适合支持的论点：模型本轮接收的是经过组织的一组信息；输入框中的需求只是其中一部分。把所有资料一次性塞入并不是唯一做法，系统也可以先提供文件路径等线索，再通过工具获取具体内容。

使用边界：这是一篇厂商工程经验文章。文中的“attention budget”等解释性措辞不宜转写成严格的物理定律，也不能据此断言每增加一个 Token 都必然降低效果。

阅读范围：已读取可获取的文章正文；未复现其中性能判断。

### S2｜产品、模型与执行环境的分工

**Claude Code — [How Claude Code works](https://code.claude.com/docs/en/how-claude-code-works)**，持续更新的英文官方文档，难度较低。

重点阅读 *The agentic loop*、*What Claude can access* 和 *The context window*。它将模型、工具、上下文管理和执行环境放到同一流程里，并列举历史消息、文件内容、命令输出、项目规则及已加载 Skills 等上下文内容。

适合支持的论点：用户使用的是一个围绕模型运行的产品。产品负责提供工具、管理上下文和连接执行环境。模型生成的工具请求经过执行，结果才成为后续判断的依据。

特别有用的细节：该文档说明 MCP 工具定义可以按需加载；不能把“已安装很多工具”画成“每一轮必然完整发送全部 Schema”。

使用边界：这些加载方式属于 Claude Code 的具体实现，不能直接当作所有聊天产品或 API 的规范。

阅读范围：已读取架构、上下文与执行相关章节；页面末尾的使用建议未完整展开。

### S3｜输入如何随会话增长

**Claude Code — [Explore the context window](https://code.claude.com/docs/en/context-window)**，持续更新的英文官方说明及交互模拟，难度较低。

重点阅读 *What the timeline shows* 和 *What survives compaction*。文档区分启动时的规则、记忆、工具名称和 Skill 描述，以及执行过程中进入的文件内容、规则和反馈，并说明会话压缩后不同内容的保留或重新加载方式。

适合支持的论点：上下文是动态构建的；用户尚未输入当前需求时，系统也可能已准备部分信息。历史压缩后，界面中能翻到的原始消息与本轮实际提供给模型的内容可能不同。

使用边界：页面明确称展示数量为代表性示意，不能当成当前会话实测占比。Hooks 本身是执行代码；只有相关说明或执行返回内容被提供给模型时，才成为上下文内容。

阅读范围：已读取文字说明与表格；未操作网页中的交互模拟。

### S4｜工具定义与参数 Schema

**Claude API — [Define tools](https://platform.claude.com/docs/en/agents-and-tools/tool-use/define-tools)**，持续更新的英文官方文档，难度中等。

重点阅读 *Specifying client tools*、*Example simple tool definition*、*Tool use system prompt*。自定义工具定义包含 `name`、`description`、`input_schema`，分别说明调用名称、用途与条件、参数的形状和类型。

适合支持的论点：模型需要知道“有哪些工具、各自做什么、参数怎么填”。官方文档还直接说明，在 Claude API 中，服务会结合工具定义、工具配置和用户提供的系统提示词构建工具使用相关的系统提示内容。

使用边界：API 中分开提交的 `tools`、`system`、`messages`，与最终给模型的内部表示是两个层次。文档展示的构造示意不代表任意产品完整、逐字的内部输入。Schema 描述参数约束，实际校验、权限和执行仍由外部系统落实。

阅读范围：已读取定义、系统提示构造说明及示例章节；未运行 API 示例。

### S5｜模型输出如何进入工具循环

**Claude API — [How tool use works](https://platform.claude.com/docs/en/agents-and-tools/tool-use/how-tool-use-works)**，持续更新的英文官方文档，难度中等。

重点阅读 *The tool-use contract*、*Where tools run*、*The agentic loop (client tools)*。

它展示了完整往返：提供工具定义与消息 → 模型返回工具请求 → 应用执行 → 将结果交回 → 模型继续。模型得到的是工具接口和返回结果，而非自动拥有工具的程序实现。

适合支持的论点：一次用户任务可能触发多次模型调用；输出不只有给用户看的回答，还可能包含结构化工具请求。应区分工具定义、调用参数和执行返回值。

使用边界：客户端工具由应用执行，服务端工具由服务商基础设施执行；不能说所有工具都运行在用户电脑，也不能说每个内部循环都需要用户另发一条消息。停止也未必意味着任务成功，可能是达到输出限制等原因。

阅读范围：已读取可获取正文；未执行工具循环。

### S6｜消息角色怎样成为模型可处理的序列

**Hugging Face Transformers — [Chat templates](https://huggingface.co/docs/transformers/en/chat_templating)**，持续更新的英文官方文档，难度中等。

重点阅读开头的原理说明及不同模型的格式示例。`role`、`content` 等结构经模型对应的模板组织成 Token 序列，角色和消息边界可能使用特殊标记表示。

适合支持的论点：对话不是把所有文字无差别拼在一起；消息来源、边界及模型所需的格式都很重要。相同消息内容在不同模型中可能使用不同模板。

使用边界：这是可查看的开源模型处理路径，不能据此声称已知某个闭源聊天产品的完整内部格式。消息角色的编码方式也不等于所有平台共用同一套指令优先级规则。

阅读范围：已读取原理和模板示例；未运行示例。

### S7｜工具定义与执行代码的直接对照

**Hugging Face Transformers — [Tool use](https://huggingface.co/docs/transformers/main/en/chat_extras)**，`main` 分支英文官方文档，难度中等。

重点阅读 *Passing tools*、*Tool-calling Example*、*JSON schemas*。该文档说明：从 Python 函数生成工具 Schema 时，提取名称、参数类型与说明，解析器忽略函数实现体。随后展示工具请求和结果如何加入消息历史。

适合支持的论点：给模型一个工具，不等于把工具源代码交给它。模型可以根据接口提出请求，由程序执行真实操作。

使用边界：这一点由 Hugging Face 的具体转换机制示范；应用也可以主动提供源代码，但那是额外内容。文档天气结果属于教学示例，不能当作真实天气观测。`main` 分支的具体 API 可能变化。

阅读范围：已读取可获取正文；未运行示例。

### S8｜MCP 与工具 Schema 的关系

**Model Context Protocol — [Tools](https://modelcontextprotocol.io/specification/2025-06-18/server/tools)**，2025-06-18 版本官方规范，英文，难度较高。

重点阅读 *Listing Tools*、*Calling Tools*、*Message Flow* 和 *Tool* 数据类型。规范使用 `tools/list` 发现工具，通过 `tools/call` 调用；定义含 `name`、`description`、`inputSchema`，也支持可选的 `outputSchema`。

适合支持的论点：MCP 是应用连接外部工具服务的一种协议。它与给模型看的工具定义有关联，但不是模型本身，也不是另一个隐藏提示词。模型请求与客户端实际发出的协议调用要分开理解。

使用边界：引用固定版本用于解释接口关系，不声称这是最新版本。MCP 的 `inputSchema`、Claude API 的 `input_schema`、Hugging Face 工具格式中的 `parameters` 属于不同接口层，不能随意混用字段。

阅读范围：已读取工具发现、调用、消息流、数据类型及错误处理相关正文；未做协议兼容性测试。

### S9｜项目规则与记忆如何进入上下文

**Claude Code — [How Claude remembers your project](https://code.claude.com/docs/en/memory)**，持续更新的英文官方文档，难度较低。

重点阅读 *CLAUDE.md vs auto memory*、*CLAUDE.md files* 和文件加载方式的说明。它区分人工维护的项目规则与产品维护的记忆，并说明它们通过加载进入上下文。

适合支持的论点：“记住我的偏好”可以来自持久化信息在后续会话中重新加载；不能仅凭这一现象认定模型参数经过了重新训练。指令文件提供行为指导，执行层面的强制约束另有实现机制。

使用边界：文件名、加载范围与大小限制属于具体产品行为。本课宜解释机制，不固定讲某个当前容量数字，也不把不同产品的规则文件混成通用标准。

阅读范围：已读取前半部分的记忆、规则、导入及 AGENTS.md 相关说明；后续排错章节未完整读取。

## 文章容易讲错的地方

1. **把所有附加内容都叫系统提示词。** 应分别解释指令、材料、工具接口、历史和环境信息；它们不自动具有相同的角色与权限。
2. **把“完整输入”理解成全部已有资料。** 本轮实际提供的内容可能只是选中片段、摘要或名称，完整性是相对于这一次调用而言。
3. **把 Skill、MCP 和 Tool 当成同一物。** Skill 提供任务知识或工作方法；MCP 是连接机制；Tool 是可请求执行的操作。某些 Skill 还包含辅助脚本，但脚本要经执行机制运行。
4. **把 API 参数全画进提示词。** 模型选择、输出长度限制等调用配置，与供模型处理的内容应分别呈现；工具配置可能又由平台转成模型可见的指导，具体映射按实现说明。
5. **把工具请求当作已执行结果。** 参数符合接口形状，不说明文件已读到、查询已成功或动作已完成。
6. **把“有很多额外输入”讲成固定数量或固定占比。** 本次没有测量真实产品请求，不提供虚构 Token 占比、固定加载顺序或秘密系统提示词。
