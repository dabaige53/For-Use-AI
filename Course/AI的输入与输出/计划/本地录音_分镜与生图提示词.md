# 本地录音案例：连续镜头逻辑

版本：2026-09-16 R2。一个镜头一份 JSON；下列文件各自包含完整、可直接复制的 prompt。本文保留叙事与旁白设计，实际生图提示词以对应 JSON 为准。

内容真源：[正文](../文章/正文.md)。舞台、配色、稳定对象 ID 和动作语法见[图形动作设计](图形动作设计.md)。当前范围为文字与设计，不制作图片、动画或完整视频。

## 解释主线与预算

观众需要看清：一次用户提问，怎样经过输入组织、模型输出、程序执行和再次输入，得到给人的回答。录音承担贯穿对象，不展开纪要写法。

采用八个连续动作段，共约 180 秒。它们共享同一舞台，不是八张独立幻灯片；镜数由八次必要的理解推进决定。各段预算包含旁白、变换与理解停顿，未试读、未渲染，成片长度可在约 165—200 秒内调整。

| 段落 | 正文定位 | 时间预算 | 本段结束时新增的理解 |
|---|---|---|---|
| S01 | 开头两段 | 0—15 秒 | 用户提出目标，文件仍在外部 |
| S02 | 先看这次输入，第 1 段前半 | 15—37 秒 | 应用也提供指令 |
| S03 | 先看这次输入，第 1—2 段 | 37—57 秒 | 路径进入输入不等于内容进入 |
| S04 | 先看这次输入，第 3 段 | 57—87 秒 | 工具定义约束请求的参数 |
| S05 | 输出先交给程序，第 1—2 段 | 87—114 秒 | 模型可以生成给程序的请求 |
| S06 | 输出先交给程序，第 3 段 | 114—138 秒 | 宿主调度程序，才发生实际读取 |
| S07 | 结果成为下一次输入，第 1、3 段 | 138—163 秒 | 请求与结果被组织进下一次输入 |
| S08 | 结果成为下一次输入，第 2、4 段 | 163—180 秒 | 再次调用后，输出交给人 |

### S01｜一句话与一段录音

- **观众疑问：**说完这句话，接下来发生什么？
- **唯一新概念：**用户给出任务目标。
- **固定对象：**U 在左上，A 在左下；中间 I 的空括号逐步画出，右侧没有模型。
- **动作及含义：**从 U 展开任务原句；A 的波形保持原地。U 收为带“用户”短标的消息轮廓，副本进入 I，表示任务成为输入的一部分。右侧原句收回，留下可继续展开其他来源的空间。
- **局部真实文字：**“把这段本地录音整理成会议纪要。”角落标“教学示例”。不显示转写内容、历史消息或纪要成品。
- **旁白：**“你第一次对助手说：把这段本地录音整理成会议纪要。我们用一个教学例子，看看这句话之后发生了什么。”
- **衔接：**I 中只有蓝色任务副本；下方空位引出应用提供的其他内容。

### S02｜应用提供的指令

- **观众疑问：**输入只有我写的这句话吗？
- **唯一新概念：**应用也会提供系统指令。
- **固定对象：**U、A、I 保留；绿色 S 从应用侧来源位出现，宿主组装节点开始显露。
- **动作及含义：**S 先以括号与双短线出现，复制进 I 的第二项；I 中的 S 保留绿色轮廓，并以细线连接右侧局部展开。原句出现后收回该轮廓。U 不移动、不被改写，显示两种来源共同进入输入。
- **局部真实文字：**“系统指令（教学示例）”；“使用中文，依据取得的资料回答。”两行以内，不冒充产品隐藏原文。
- **旁白：**“应用还可以放入系统指令，比如：使用中文，依据取得的资料回答。组织输入、调用模型的这段应用程序，叫宿主。”
- **衔接：**系统指令收回 I。A 仍在外部，下一段说明宿主此刻提供了录音的什么信息。

### S03｜先知道位置，还不知道内容

- **观众疑问：**录音是不是已经交给模型了？
- **唯一新概念：**位置与内容不同。
- **固定对象：**A 固定，E 在来源位出现，U/S 在 I 内低亮可见。
- **动作及含义：**从 E 拉无箭头细线到 A，表示对应文件；E 的路径副本进入 I，右侧从 E 局部展开示例路径。路径收回，A 的波形从始至终未进入 I。关系通过“路径移动、文件留在原处”表达，不靠大段解释。
- **局部真实文字：**“录音位置”；`/audio/meeting.wav`；展开区角注“假设路径”。
- **旁白：**“这个例子里，宿主起初只提供录音的位置。路径已经进入输入，录音内容还没有。这是第一次提问，也没有此前对话。”
- **衔接：**I 已有 U/S/E，仍缺少取得内容的方法；下一段从应用侧引入 D。

### S04｜工具定义告诉模型怎么提出请求

- **观众疑问：**模型怎样知道要填什么，才能请求转写？
- **唯一新概念：**工具定义规定请求参数。
- **固定对象：**D 是金色开放接口，主槽 `file_path` 与三枚短槽可辨；D 副本加入 I 后，以连线牵出右侧真实 Schema 局部。左侧 U/S/E/I 和下方 A 持续可见。
- **动作及含义：**先同时亮起 D 的名称与右侧 `name`；再让 D 主槽与 `properties` 中的 `file_path` 对齐。`required` 的短线指回同一槽，表示必填；`type: string` 表示填入文本。其余三槽短暂亮起，标明还有可选项，然后所有局部内容收回 D，I 四项完整。这里只讲一个参数如何受定义约束，不逐个浏览说明文档。
- **局部真实文字：**使用下方“Schema 局部视窗”的两个焦点。焦点切换时 D 与 I 不消失；每次仅一处主要高亮。中文旁注“文本”“必填”。工具用途由旁白说明，完整英文 description 留在来源文件。
- **旁白：**“宿主还提供本次可用的工具定义。这里用公开的转写工具 transcribe_audio。它的 inputSchema 规定，file_path 要填文本，而且必填。定义告诉模型怎样提出请求；它本身还没有执行转写。”
- **衔接：**右侧展开收空，U/S/E/D 在 I 中保持各自边界；输入介绍至此完成，下一段才出现 M。

### S05｜模型生成给程序的输出

- **观众疑问：**模型现在会直接写纪要吗？
- **唯一新概念：**输出也可以是一条工具请求。
- **固定对象：**I 保持中左，M 首次在右侧出现；D 保留在输入侧，C 是模型输出端新出现的对象。
- **动作及含义：**I 的副本沿箭头进入 M，随后 C 在输出端生成。局部展开 C：工具名称与 D 对齐；C 内已有生成的 `file_path` 值，与 E 的路径用无箭头线对应。再显露另外三个参数值后收回。不要让路径绕过模型直接填入 C，或把 D 变成 C。C 经过宿主分派节点走向下方，给人的回答位仍空。
- **局部真实文字：**`transcribe_audio` 与下方“调用参数局部视窗”。所有值标“假设参数”；主焦点是 `file_path`，其余三项低亮。`model` 旁短注“转写模型”。
- **旁白：**“模型收到输入后，可以先生成转写请求：选择这个工具，把录音路径作为参数。这些是假设值，其中 model 选择转写所用的模型。这份输出交给程序处理，此刻录音还没被读到。”
- **衔接：**C 到达宿主执行入口，保留请求副本作后续匹配。A 原地不动，X 此时才显露。

### S06｜宿主把请求变成实际操作

- **观众疑问：**谁真的读取录音？
- **唯一新概念：**外部程序执行操作。
- **固定对象：**C、X、A 构成下方焦点；上方 I/M 留低亮锚点。
- **动作及含义：**宿主调度节点接到 C，点亮通向 X 的执行线。X 按路径读取 A：波形副本第一次进入扫描口，原文件仍在。扫描线穿过副本，输出端生成独立的 R，青白短横线与时间刻度表明它是返回文字。请求与返回边缘出现同形配对标记；不把匹配标记写进工具参数。
- **局部真实文字：**“宿主执行”“转写程序”“转写结果（示意）”；R 只见 `00:12`、`00:25` 及短横线，不编造会议原句或返回 JSON。
- **旁白：**“宿主接收请求，按实际访问和执行条件调用转写程序。现在，程序才读取录音。假设转写成功，它返回文字结果；提示词里的要求，并不会自己变成程序权限。”
- **衔接：**X 停止扫描，R 沿底部回程线离开 X，去往宿主组装节点，不直接飞到 M。

### S07｜结果回到输入

- **观众疑问：**返回的文字怎样让模型继续？
- **唯一新概念：**结果要成为下一次调用的输入。
- **固定对象：**C 副本与 R 在宿主组装节点配对，原 U/S/E/D 分组仍在 I。
- **动作及含义：**宿主将 R 与对应 C 配对，再把二者副本加入 I 的新增区；旧四项仅保留本例继续需要的部分，低亮显示，新两项高亮。I 括号向下伸展，标签从“首次输入”变为“下一次输入”。此时才产生请求记录和结果记录，不补画虚构的早期消息。R 曾经返回与 R 已进入输入形成两个可见状态。
- **局部真实文字：**“请求记录”“工具结果”“下一次输入”；旧分组旁短标“本次仍需的信息”。不显示历史仓库、完整聊天列表或全部已安装工具。
- **旁白：**“宿主把结果与对应请求，连同仍需使用的原有信息，组织成下一次输入。保存的记录不一定全部送入。若工具返回错误，带回来的就是错误，不能当作已经取得录音内容。”
- **衔接：**下一次 I 完整落定，宿主点亮再次调用的箭头。此时停半拍，让观众看到“新增内容”再启动第二次调用。

### S08｜同一个模型，另一种输出去向

- **观众疑问：**最后交给用户的答案从哪来？
- **唯一新概念：**同一任务可以经过多次模型调用。
- **固定对象：**M 身份和位置不变；下一次 I 从相同输入口进入；H 从相同输出口生成。
- **动作及含义：**第二次调用后生成 H，经宿主同一分派节点沿上路进入给人的回答位。下方 C/X/R 路线保留低亮，用户任务 U 仍是最初那条。最终只高亮两条已经走过的输出路径，不重播整个流程。
- **局部真实文字：**“会议纪要”；两处短标“给程序”“给人”。H 内只用中性段落形状，无写盘或发送成功图标。
- **旁白：**“用户只问了一次，模型已经被调用两次。取得转写后，它可以生成给人看的纪要。模型输出既能交给人，也能交给程序；执行结果再回到输入，对话就能继续。”
- **结束状态：**一眼能沿 I→M→C→X→R→I 找到循环，也能沿 M→H 找到最终回答。不是预设只有两次调用的一般定律。

## Schema 局部视窗

真实定义见[完整 JSON](../素材/来源/whisper-mcp/transcribe_audio.schema.json)及[固定提交说明](../素材/来源/whisper-mcp/README.md)。以下是从该定义取出的字段投影，省略 description 和未聚焦的属性，旁标“原定义局部”。不是完整工具注册对象，不可用于直接执行。保留 MCP 的 `inputSchema`，不改成 `parameters`。

焦点 A（与 D 的名称对应，随后展开参数父层级）：

```json
{
  "name": "transcribe_audio",
  "inputSchema": {
    "type": "object"
  }
}
```

焦点 B（同一对象的参数局部，占右侧视窗；D、I、A 均留在画面）：

```json
"inputSchema": {
  "properties": {
    "file_path": { "type": "string" }
  },
  "required": ["file_path"]
}
```

焦点 B 是 JSON 片段，`required` 与 `properties` 同级。用同一条连接线说明它约束主槽，不用新镜头重新介绍 `required`。可选的 `model`、`language`、`output_format` 作为 D 的三枚短槽名称出现，暂不展开 description 或完整 enum；完整源码仍可核验。

## 调用参数局部视窗

S05 展开 C 的参数内容：

```json
{
  "file_path": "/audio/meeting.wav",
  "model": "large",
  "language": "zh",
  "output_format": "timestamps"
}
```

工具名 `transcribe_audio` 标在 C 顶部，与参数对象分开。此处只展示模型请求携带的语义信息，不声称这是某个模型 API 的完整输出封装。宿主可将模型请求转换为 MCP `tools/call`；MCP 调用中使用 `params.name` 与 `params.arguments`。定义、模型输出、协议调用分属不同层，片中不展开三套外层 JSON。

配对标记是教学图形，用来跟踪请求和返回；它不是新增 Schema 字段。MCP JSON-RPC 请求和响应通过 `id` 对应，宿主还需维护与模型端请求的关联，不暗示各层共用同一个真实 ID。R 的时间刻度与文字线条是内容示意，未核验转写实现的返回结构，也没有实际转写日志。

## 文档验收与制作边界

- 第一次输入只有本例的 U/S/E/D；C 和 R 在生成后才进入后续上下文。
- S01—S04 右侧只作来源局部展开，S05 首次引入 M。
- 每次展开都指回一个已有对象，并有收回动作；S04 的文字内容不脱离 D/I/A 的关系。
- 模型生成 C，宿主调度 X，X 读取 A；R 先回宿主，再进入 I，最后才第二次调用 M。
- `inputSchema`、唯一必填 `file_path` 与来源一致；参数值、系统句、文件和成功路径均为教学假设。
- 图形去掉长句后仍能追踪动作；加回局部文字后能确定具体参数的作用。实际画面可读性待后续制作验收。
- 本版不讨论模型推理内容，不把推理当工具请求；不演示纪要分类、真实音频处理、写盘或外部发送。
