# 第六篇任务命名与分类研究

## 结论

第 1 页不应罗列「生图、HTML、脚本、完整制作」等媒介或阶段，也不应把「未看样片就渲染完整视频」这样的风险状态当成任务。每个点应是**一次能让读者看见、操作、核对或据此作决定的工作**；工具只在读者无法从任务名推知实现方式、或该方式会改变可判断范围时，放进括号或短副标题。

推荐的标题公式是：**动词 + 具体对象 +（必要的方法／范围）**。例如：

| 层级 | 写法 | 例子 | 放在哪里 |
| --- | --- | --- | --- |
| 目标 | 想帮助谁完成什么判断或行动 | 判断页面的信息应怎样组织 | 文章或页面引言，不是地图点 |
| 任务 | 本轮做出什么可观察对象 | 制作可点击的交互草稿（HTML） | 第 1 页与地图的主标题 |
| 方法／工具 | 用什么形成该对象 | HTML、图像生成模型、脚本、人工走查 | 括号、短副标题或图例 |
| 验证动作 | 看什么来决定下一步 | 请人完成关键操作并说出结果；核对一组样本 | 「本次看什么」短行 |
| 产物 | 已得到的对象 | 可点击草稿、试算结果、15 秒样片 | 任务完成的可见证据 |
| 条件 | 为什么这次可停在此处或可扩大 | 只模拟数据；字段口径已确认 | 小标签 |
| 风险状态 | 何时应缩小投入 | 需求未定、接口未核对、未看动态样片 | 低饱和警示提示，不能与任务同列 |

这是面向本课的**设计推断**，不是声称已通过受众测试。它与原文的「可观察、可验证成果」原则相符，也把用户要求保留的具体表达（如「使用生图模型生成图片」「HTML 元素／页面验证」）落实为可读的任务名，而不是抽象的「比较小样」「查证事实」。

## 为什么旧清单难以理解

当前 HTML 与《06七页具体工具文案》把至少五种不同性质的条目排在同一层：

| 当前写法或类型 | 问题 | 改写方向 |
| --- | --- | --- |
| 用生图模型生成风格草图 | 能看到工具和大致用途，但不知道草图要支持哪一个判断 | 生成两张视觉方向图（生图模型） |
| 用 HTML 搭页面看布局 | 只有媒介和笼统动作；没有页面对象、范围或判断点 | 制作一页内容布局草稿（HTML） |
| 用小脚本试算几条真实数据 | 「几条」和「试算」没有说明算什么、如何核对 | 检查一组数据的计算结果（脚本） |
| 按确认原型完成一个页面 | 是可用的任务骨架，但「一个页面」仍缺业务对象 | 按确认原型完成指定页面 |
| 样片通过后制作完整动画 | 「完整制作」是扩大范围的阶段，不是可比较的任务类型 | 制作 15 秒状态切换样片；确认后扩展为完整动画 |
| 需求未定就搭建完整网站 | 这是风险状态，不是读者可选择的正常任务 | 低饱和警示：需求未定时，不扩大为全站开发 |
| 让 AI 追问当前需求缺口 | 是方法，读者看不到完成后的东西 | 列出当前需求的待确认项（AI 追问） |
| 让 AI 检索指定技术文档 | 研究范围和欲判定的事实缺失 | 核对某接口是否支持批量上传（官方文档） |
| 按共享接口分工多个 Agent | 是协作安排，不能单独成为交付 | 交付可集成的文件转换模块（共享输入输出） |

上述判断直接对应原文两点：第六节要求选择能支撑**当前关键判断**的最小成果，并说明它不能推出什么；第七节要求拆分后有清楚输入、可检查输出和可接受的失败范围。原文也明确说明 HTML、九宫格和小脚本没有固定的投入属性，不能因为叫作「HTML」或「脚本」而自动落在一个象限。见[原始文章第六至九节与附录 A](../../../资料库/02-知识与原文/AI协作框架/ai_collaboration_framework.md)；[原始对话中用户对 HTML 原型、九宫格与小脚本的澄清](../../../资料库/02-知识与原文/AI协作框架/AI不可能三要素_对话.md)。

## 第 1 页：按读者熟悉的工作类型分组

内容分类建议采用六类常见工作：**学习与提问、检索与比较、写作与整理、图片与动画、网页与交互、数据与自动化**。分类只帮助读者找到相近工作，不决定象限，也不把「完整制作」或「复用」另列为阶段；它们会出现在相应媒介的具体任务中。以下是 24 条候选内容，不规定第 1 页必须用六栏、每栏四项：版面可分栏、分组卡片或分批呈现。数量是当前覆盖度的结果，不是必须凑满的指标；某一项若无法写出对象和判断，应删掉或回到材料中补齐。

| 栏目 | 候选任务名 | 短方式／本次产物 |
| --- | --- | --- |
| **学习与提问** | 写出当前需求的待确认项 | AI 追问后得到问题清单 |
|  | 用一个例子解释陌生概念 | 术语、例子与适用边界 |
|  | 把模糊想法改写成使用场景 | 谁在何时要作什么判断 |
|  | 用正反例说明一条业务规则 | 可对照的规则说明 |
| **检索与比较** | 核对一项关键说法的原始来源 | 来源链接与支持范围 |
|  | 比较两个方案的关键差异 | 同一约束下的取舍表 |
|  | 找出一项技术限制 | 官方文档或接口返回 |
|  | 标注参考作品可借用的部分 | 保留项、排除项与参考图 |
| **写作与整理** | 写出一段面向读者的解释 | 一段可审阅正文 |
|  | 重写一页需求说明 | 保留项、改动项与边界 |
|  | 按样章写出一个章节草稿 | 指定章节的初稿 |
|  | 按确认模板生成一页报告 | 有确定输入的报告页 |
| **图片与动画** | 生成两张视觉方向图（生图模型） | 可并排比较的图片 |
|  | 生成一张人物与场景参考图（生图模型） | 角色、场景与风格依据 |
|  | 制作九宫格状态分镜（生图模型） | 初始、触发、变化、结果 |
|  | 制作 15 秒状态切换样片 | 可播放的动态片段 |
| **网页与交互** | 制作一页内容布局草稿（HTML） | 真实文案的页面层级 |
|  | 制作可点击的交互草稿（HTML） | 只模拟关键操作 |
|  | 对比两种信息结构（HTML） | 同一内容的两个页面 |
|  | 用手机走查单页点击与滚动 | 关键操作记录 |
| **数据与自动化** | 检查一组数据的计算结果（脚本） | 可手工核对的计算结果 |
|  | 查看一个接口的字段与返回格式（脚本） | 实际返回与字段说明 |
|  | 用异常值试跑一条计算规则（脚本） | 边界输入的结果 |
|  | 转换一份字段映射已确认的表格（脚本） | 输入、输出与映射记录 |

### 使用这些标题的规则

1. **对象优先，工具后置。**「制作可点击的交互草稿（HTML）」先让读者知道要看什么，再说明用 HTML；「用 HTML 验证」无法让读者知道验证对象。
2. **一个标题只承载一个主要判断。**「生成图片、搭页面、验证体验」应拆开，因为三者分别产出图、页面和体验证据。若同一页面同时要验证布局与点击，先写两项，除非它们只能作为同一任务被判断。
3. **检查可以是副行，也可以是独立任务。**当检查对象与结果明确时，它本身就是任务，例如「检查一组数据的计算结果（脚本）」「测试一个按钮的跳转结果」「核对一个接口的返回格式」；若只是说明某项产物要看什么，则放副行。例如「制作九宫格状态分镜」下可写「看状态与因果，不判断节奏」。
4. **「完整」「全量」「整套」必须带范围。**它们只说明投入扩大，不说明要产出什么。应改成「完成指定课程章节」「处理指定时间范围的文件」或「制作指定段落的动画」。
5. **风险状态离开任务池。**页面可用低饱和警示统一写「关键条件未确认时，停止扩大范围」，再举「未看样片就渲染完整视频」「口径未核对就跑全量数据」为触发例；这些例子不占正常任务点。

## 同一任务怎样出现在不同象限

任务名保持稳定，象限位置由一次**任务实例**决定：`任务 + 当前要判断的事 + 已有依据 + 下一次反馈前的投入`。工具不是坐标，标题也不是坐标。

以「制作可点击的交互草稿（HTML）」为例：

| 当前实例 | 适合呈现的位置 | 原因与标签 |
| --- | --- | --- |
| 还不知道关键操作应怎样安排，只做一屏模拟内容 | 探索 | `看：读者能否指出需要的操作`；反馈快、方向待定 |
| 页面范围、关键操作和原型已确认，只交付演示用单页 | 轻量交付 | `已确认：操作与原型`；范围有限，可直接验收 |
| 已验证关键流程，继续接入权限、真实数据和多页面 | 深度建设 | `已确认：流程与接口`；投入和反馈周期都扩大 |
| 不知道页面帮助谁作什么判断，已开始全站与后端 | 高暴露提示 | 不是 HTML 任务的天然位置，而是「缩小范围、恢复反馈」的状态 |

七页可据此处理：

| 页 | 内容处理 |
| --- | --- |
| 1 | 六类任务池，只显示稳定任务名与短产物；版面不必把类别等同为六栏。 |
| 2 | 每个点带一个条件标签；同名任务可在不同条件下出现多个实例。图例说明「位置表示这一次的条件，不评价工具」。 |
| 3–6 | 不重新定义任务；在同一任务名旁高亮「此知识状态下为什么先做它」及本次要看的证据。允许跨栏、回退和重复使用。 |
| 7 | 用「这次能判断什么／还不能证明什么」收束。例如九宫格不能判断节奏，HTML 草稿不能证明真实后端，小范围试算不能证明全量数据可靠。 |

这也符合原始对话中用户的明确修正：原型可以在「什么都不知道」时帮助发现问题，关系是可交叉使用的倾向，不是必须逐关通行的流程。原文第九节的两个案例同样允许从规则、样本或粗糙页面等不同起点进入。

## 用户理解验收法

不要把「读者会懂」写成已证实的结论。制作前可用以下低成本检查来决定标题是否留下；这是建议的验收方法，尚未执行。

| 检查 | 给读者的材料 | 通过信号 | 失败后的处理 |
| --- | --- | --- |
| 单卡复述 | 只给主标题，不给工具说明 | 读者能说出「会得到什么」和「用来判断什么」 | 补具体对象或把判断写进副行 |
| 选择理由 | 给出两个相近标题及其条件 | 读者能说出「要做什么、会交付什么、什么情况下选它」 | 补具体对象、结果或条件标签 |
| 条件选点 | 给同一任务的两个情境 | 读者能说明为何一个在探索、另一个在轻量或深度建设 | 增加「已确认／只模拟／全量」条件标签 |
| 反证边界 | 给九宫格、HTML 草稿、一组数据试算三项 | 读者能说出各自**不能**证明的结论 | 在第 7 页补「本次不判断」 |

验收对象应是本课定位的「已有 AI 使用经验、无需编程基础」读者；但人数、招募方式和通过阈值尚未决定。没有实际读者反馈前，不能声称这些标题已经通俗或更易理解。

## 证据、推断与边界

### 已确认的课程内依据

- [课程讨论决策](讨论决策.md)确认第 1 页要按任务类型展开，第二页把行动映射到投入与对齐，知识状态只表示倾向；并在后续反馈中要求以「生图模型生成图片」「HTML 元素验证」一类具体工具与产物描述替代抽象标签。
- [原始文章第六节](../../../资料库/02-知识与原文/AI协作框架/ai_collaboration_framework.md)把文字、图片、HTML、接口返回、样本计算、人工模拟都列为可能的最小可判断成果，同时规定成果能支持的结论有限。
- [原始文章第七节及附录 A](../../../资料库/02-知识与原文/AI协作框架/ai_collaboration_framework.md)要求以可检查的输出拆分任务，且将问题澄清、概念学习、研究、文字、外显、技术试验、真实试用和复用都纳入可交叉使用的活动。
- 当前 [具体工具文案](06七页具体工具文案.md)和 [任务地图 HTML](../06-行动与投入/配图/06-task-map.html)确实把任务、工具、阶段与风险状态混排；本报告的改写对照针对这一材料。

### 外部一手来源

本次用 Exa 在 3 个检索方向审阅 24 个候选结果，并阅读了以下 4 个一手页面；相同 URL 已去重。它们支持命名和标签设计的有限原则，**不**直接证明本课的六类分类或候选清单有效。

- GOV.UK 将用户需求与具体任务区分，要求需求从用户可识别的行动出发；它也建议按用户看得懂的任务来划定服务范围，避免用组织结构或技术选择决定任务形状。[Identify user needs](https://guidance.publishing.service.gov.uk/writing-to-gov-uk-standards/plan-manage-content/identify-user-needs/)；[Getting the scope of your transaction right](https://www.gov.uk/service-manual/design/scoping-your-service/)
- Microsoft 的标题指引要求把重要信息前置、标题具体、同层标题保持平行，并以读者能完成的事组织内容。[Headings](https://learn.microsoft.com/en-us/style-guide/scannable-content/headings)
- W3C 的 WCAG 解读要求标签或说明让使用者知道预期输入；在不增加无关信息的前提下，具体标签和必要说明可降低误解。这里借用的是「标题应指出对象与必要条件」的可用性原则，并非把 PPT 点当作网页表单。[Labels or Instructions](https://www.w3.org/WAI/WCAG22/Understanding/labels-or-instructions.html)

### 本报告的设计推断

- 「动词 + 具体对象 +（必要方法／范围）」是将上述原则与课程原文结合后的命名模板；它不是任何来源规定的唯一格式。
- 六类与 24 项是为覆盖原文活动、避免纯工具分类和避免把交付阶段另立一类而作的候选内容；最终栏目数量、版面和条目应以读者验收调整。
- 同一稳定任务在不同条件下进入不同象限，是原文「工具不天然定性、活动可交叉使用」的教学化表达；没有量化评分或受众实验支持，不能把它画成精确预测。

### 尚缺的证据

1. 尚未以目标读者测试题名是否真能被正确复述。
2. 尚未确定第 1 页版面能容纳多少项、是否以任务卡分批展示；这属于后续视觉设计决定。
3. 没有任何来源或原文证明某个工具天生在某一象限，故不应在图上把工具永久定性。
