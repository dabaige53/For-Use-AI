# 第六篇任务清单：按读者要完成的事情命名

## 定义与写法

本课中的任务项，是读者可以交给 AI 或与 AI 一起完成的一项具体工作。名称应让人知道做什么、对象是什么，并能预期得到什么结果。结果可以是图片、网页、文档，也可以是有依据的解释、比较或检查结论。

采用“动作＋具体对象／结果”，在必要时补充“生图模型、HTML、脚本”等方式。通用任务目录保留可复用名称；执行时再代入实际文章、数据、页面和规则，不为了显得具体而虚构订单、金额或固定数量。

依据：[原始文章](../../../资料库/02-知识与原文/AI协作框架/ai_collaboration_framework.md)第六至九节及附录 A；[任务命名研究](06任务命名研究.md)。GOV.UK 强调采用用户能识别的语言表达想完成的事，Microsoft 强调名称具体、重要信息前置及同层表述一致。将这些原则用于本课的任务目录，是设计推断，不是已通过受众实验的结论。[GOV.UK 用户需求](https://www.gov.uk/service-manual/user-research/start-by-learning-user-needs)、[Microsoft 标题写法](https://learn.microsoft.com/en-us/style-guide/scannable-content/headings)。

## 旧写法的主要问题

| 旧写法 | 问题 | 新写法 |
| --- | --- | --- |
| 比较小样 | 没有比较对象 | 比较两种页面布局 |
| 使用 HTML 元素验证 | 没说做什么、验证什么 | 制作可点击的网页草稿（HTML） |
| 用小脚本试算数据 | 没说明试算要完成的判断 | 检查一组数据的计算结果（脚本） |
| 用现有 Skill 完成明确任务 | 用“任务”解释“任务”，读者仍不知道做什么 | 按模板写一份报告；Skill 是可选执行方式 |
| 按共享接口分工多个 Agent | 协作安排，没有说明工作成果 | 串联多个脚本完成数据处理；是否由多个 Agent 执行另行决定 |
| 未看样片就渲染完整视频 | 风险状态混进正常任务 | 任务写“制作完整动画”，风险条件在后续象限页解释 |

验证本身可以是任务，例如测试接口、检查计算、试走操作流程。它需要明确的检查对象和检查结果，不必一律移入副说明。

## 重列的 30 项任务

以下六类是内容分组，不要求 PPT 排成六栏，也不是执行顺序。任务名是页面候选文案；右列用于校对定义，不要求全部放进图里。

### 学习与提问

| 任务名 | 完成后能得到什么 |
| --- | --- |
| 用例子解释一个陌生概念 | 对概念含义与适用情境的解释 |
| 对比两个容易混淆的概念 | 两者相同点、不同点及例子 |
| 把想法整理成需求清单 | 需要完成的内容与范围 |
| 列出需求中待确认的问题 | 会影响后续工作的未决问题 |
| 用正反例说明一条规则 | 可以据此判断对错的规则说明 |

### 资料与方案

| 任务名 | 完成后能得到什么 |
| --- | --- |
| 查找一项说法的原始出处 | 来源及其实际支持的内容 |
| 查清工具是否支持所需功能 | 文档依据、支持条件或仍需试验的部分 |
| 整理一个主题的资料与来源 | 可以回查的资料清单 |
| 比较两种方案的优缺点 | 同一需求下的差异与取舍依据 |
| 查找已有方案的失败案例 | 具体失败情况及与当前任务的关系 |

### 写作与整理

| 任务名 | 完成后能得到什么 |
| --- | --- |
| 拟写一篇文章的提纲 | 可审阅的内容顺序与层级 |
| 按模板写一份报告 | 满足指定用途的报告草稿 |
| 把长文整理成要点清单 | 保留原意的主要信息 |
| 按反馈修改一段文字 | 对应具体问题的修改稿 |
| 按要求检查一份文档 | 遗漏、不一致或未达要求之处 |

### 图片与动画

| 任务名 | 完成后能得到什么 |
| --- | --- |
| 生成一组风格参考图（生图模型） | 可直接比较视觉方向的图片 |
| 按参考图生成文章配图 | 与文章用途及参考方向对应的配图 |
| 生成九宫格动画分镜（生图模型） | 动画状态、构图与变化顺序 |
| 制作一小段动画样片 | 能播放并检查节奏、连续性的片段 |
| 按确认分镜制作完整动画 | 指定范围内的动画成片 |

### 网页与交互

| 任务名 | 完成后能得到什么 |
| --- | --- |
| 制作页面布局草稿（HTML） | 可查看内容位置与层级的页面 |
| 制作可点击的网页草稿（HTML） | 能试操作与页面响应的原型 |
| 用真实文案检查页面布局 | 排版、长度或信息层级的问题 |
| 请使用者试走网页操作流程 | 实际操作中的误解、阻碍与遗漏 |
| 按确认原型完成一个网页 | 达到已确认内容与交互要求的网页 |

### 数据与自动化

| 任务名 | 完成后能得到什么 |
| --- | --- |
| 检查一组数据的计算结果（脚本） | 与预期计算对照后的结果或差异 |
| 测试接口能否返回所需数据（脚本） | 真实返回、失败情况及可用范围 |
| 清理表格中的重复与缺失数据 | 按已定规则处理的表格及异常记录 |
| 按规则批量转换文件（脚本） | 所需格式的文件及失败记录 |
| 串联多个脚本完成数据处理 | 从原始输入到最终结果的处理流程 |

## 如何接到后六页

第一页回答有哪些具体工作可选。第二页定位一次具体安排，而不是把工具或任务永久分到某个象限。例如“制作可点击的网页草稿”：只模拟一个未确定的流程，与按已确认要求交付一个演示网页，其对齐依据不同；为它接入完整后端又扩大了工作范围。

第三至六页保留任务名称，在侧边解释同一任务为什么值得优先选择：不懂流程时可以用网页草稿帮助认识；知道某个点击行为尚未确认时，可以用它试验；有偏好说不清时，可以对照草稿指出差异；没有意识到操作问题时，可以请他人实际点用。

颜色表示该次安排的象限。任务名称、方式、范围和依据分开维护，避免为凑四色而把错误做法当成任务。“未看样片就完整渲染”等内容作为风险条件说明。

第七页汇总成果与判断的对应关系：参考图看风格，分镜看状态，样片看节奏，可点击网页试操作，脚本输出核对计算。不把一种成果当成所有方面都已验证。

## 理解检查

先请符合本课定位的读者只看名称，说出“要做什么”“会得到什么”“什么时候会选它”。若读者必须听讲师解释缩写才能回答，就改写名称；若只是实际对象未指定，执行时填入对象即可。
