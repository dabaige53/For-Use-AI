语义退火

复杂的工程问题往往需要创新最优解，需要更高能量跨越高耸的地形到达更远的山谷  
常用的技巧有模型内部的动态温度，这是很多模型的工程优化，而对使用者则可以先发散思维，获得足够能量后再用约束条件收敛到创新解法

![image](images/d0551b9a5b34235ffdc90b139e26e3fc01f277ab.jpeg)

### 先推理后结论

单独拎出来是因为很多人喜欢让模型先得到结论，但后续的推理都是基于这个结论锚点做采样塑造地形轨道，或者说都是为了圆这个结论而做的辩护

![image](images/36d4317f640042217f77f8c620a209adf99ac6da.png)

### 入戏与共振采样

特定设定引导模型进入某个场景后，多步推理产生的一连串 token 会表现出高度共振，滚雪球式的形成极深的峡谷，在对话轮数越少时效果越好，噪声越少塑造越牢固

![image](images/40529340967e5adbfb2d549fdce46a9110b0c0b7.jpeg)

### 轨道弹弓

这个技巧更多会用于越狱测试（写出来不是教大家越狱！而是提供模型安全能力测试的思路，切勿以身试法），安全性高的模型，敏感词区域有更高的壁垒  
通过构建共识性强的能量轨道并引发共振采样，给小球累积足够强烈的动能后再借助惯性突破安全限制

：# AI核心动画需求说明

## 一、总体需求

需要制作 **3个核心动画**。

三个动画用于解释AI从模型能力形成，到一次对话运行，再到Agent实际执行任务的完整链路。

整体逻辑：

**模型能力形成 → 一次对话运行 → Agent执行动作**

三个动画之间应保持统一的概念体系和视觉体系，可以连续呈现，也可以独立使用。

暂时不扩展更多核心动画。

# A01｜模型能力如何形成

## 核心问题

**模型为什么会有这些能力？**

## 需要表达的核心内容

从训练角度解释模型能力的来源。

核心流程：

**Data → Token → Training → Parameters → Model Capability**

需要包含：

* 数据进入训练过程
* 文本被转换为Token
* 模型根据已有内容预测后续Token
* 将预测结果与实际训练数据进行比较
* 根据误差调整模型参数
* 训练过程大量重复
* 最终形成训练后的模型及其参数能力

## 需要明确表达的结论

**训练会改变模型参数。**

普通用户后续使用模型时，不等于每进行一次对话都重新训练模型。

## 表达边界

不需要深入数学公式。

不需要展示真实神经网络内部结构。

不需要展示虚构的参数值或Token概率。

重点是建立：

**数据 → 训练 → 参数 → 模型能力**

这一基础关系。

---

# A02｜一次对话如何运行

## 核心问题

**我输入一句话以后，一个AI产品内部发生了什么？**

## 重点要求

这个动画**不是单独解释Context的定义**。

需要从一次真实的用户输入开始，解释一个AI产品在调用模型之前和之后发生的完整过程。

首先可以建立最小理解：

**User Input → Model → Output**

然后说明真实AI产品通常并不是简单地把用户输入直接交给模型。

## 需要表达的信息来源

一次模型调用中，产品可能组织：

* User Input
* System Prompt / System Instructions
* Developer / Product Instructions
* Project Rules
* Conversation History / Conversation State
* Files / References
* Memory
* Tool Definitions
* Environment Information
* Permission Information
* 其他本轮任务需要的信息

这些内容经过产品组织以后，形成：

**Model Input**

进一步可以理解为：

**Current Context**

然后：

**Current Context → Model → Model Output**

## Context的表达要求

不要从抽象定义开始解释Context。

需要让用户先看到：

**不同来源的信息是怎样被组织成一次模型输入的。**

然后再说明：

> 这些模型本轮真正能够使用的信息，可以理解为Current Context。

需要表达：

**Prompt只是Context的一部分。**

同时需要说明：

**文件存在、历史存在、Memory存在，并不意味着它们一定完整进入本轮模型输入。**

## Model Output需要表达两种主要情况

模型输出可能是：

### 1. Text Response

直接形成文字回答。

### 2. Tool Call

模型提出调用某个工具的请求。

A02在Tool Call产生以后结束，并进入A03。

## A02核心链路

**User Input

* System Instructions
* Rules
* Conversation
* Files
* Memory
* Tool Definitions
* Environment / Permissions
  → Assemble Model Input
  → Current Context
  → Model
  → Output**

其中：

**Output → Text Response**

或者：

**Output → Tool Call**

# A03｜Agent如何执行动作

## 核心问题

**当模型产生Tool Call以后，一个Agent怎样真正执行动作？**

## 重点要求

需要明确区分：

**模型产生动作请求**

和

**外部系统真正执行动作**

模型本身不直接进入电脑、数据库、文件系统或业务系统进行操作。

模型产生：

**Tool Call**

之后，需要由模型之外的系统负责实际执行。

## 核心流程

**Model
→ Tool Call
→ Harness
