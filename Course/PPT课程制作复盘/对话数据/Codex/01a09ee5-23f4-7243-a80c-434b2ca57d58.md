：# AI核心动画需求说明

## 一、总体需求

需要制作 **3个核心动画**。

三个动画用于解释AI从模型能力形成，到一次对话运行，再到Agent实际执行任务的完整链路。

整体逻辑：

**模型能力形成 → 一次对话运行 → Agent执行动作**

三个动画之间应保持统一的概念体系和视觉体系，可以连续呈现，也可以独立使用。

暂时不扩展更多核心动画。

---

# A01｜模型能力如何形成

## 核心问题

**模型为什么会有这些能力？**

## 需要表达的核心内容

从训练角度解释模型能力的来源。

核心流程：

**Data → Token → Training → Parameters → Model Capability**

需要包含：

* 数据进入训练过程
* 文本被转换为Token
* 模型根据已有内容预测后续Token
* 将预测结果与实际训练数据进行比较
* 根据误差调整模型参数
* 训练过程大量重复
* 最终形成训练后的模型及其参数能力

## 需要明确表达的结论

**训练会改变模型参数。**

普通用户后续使用模型时，不等于每进行一次对话都重新训练模型。

## 表达边界

不需要深入数学公式。

不需要展示真实神经网络内部结构。

不需要展示虚构的参数值或Token概率。

重点是建立：

**数据 → 训练 → 参数 → 模型能力**

这一基础关系。

---

# A02｜一次对话如何运行

## 核心问题

**我输入一句话以后，一个AI产品内部发生了什么？**

## 重点要求

这个动画**不是单独解释Context的定义**。

需要从一次真实的用户输入开始，解释一个AI产品在调用模型之前和之后发生的完整过程。

首先可以建立最小理解：

**User Input → Model → Output**

然后说明真实AI产品通常并不是简单地把用户输入直接交给模型。

## 需要表达的信息来源

一次模型调用中，产品可能组织：

* User Input
* System Prompt / System Instructions
* Developer / Product Instructions
* Project Rules
* Conversation History / Conversation State
* Files / References
* Memory
* Tool Definitions
* Environment Information
* Permission Information
* 其他本轮任务需要的信息

这些内容经过产品组织以后，形成：

**Model Input**

进一步可以理解为：

**Current Context**

然后：

**Current Context → Model → Model Output**

## Context的表达要求

不要从抽象定义开始解释Context。

需要让用户先看到：

**不同来源的信息是怎样被组织成一次模型输入的。**

然后再说明：

> 这些模型本轮真正能够使用的信息，可以理解为Current Context。

需要表达：

**Prompt只是Context的一部分。**

同时需要说明：

**文件存在、历史存在、Memory存在，并不意味着它们一定完整进入本轮模型输入。**

## Model Output需要表达两种主要情况

模型输出可能是：

### 1. Text Response

直接形成文字回答。

### 2. Tool Call

模型提出调用某个工具的请求。

A02在Tool Call产生以后结束，并进入A03。

## A02核心链路

**User Input

* System Instructions
* Rules
* Conversation
* Files
* Memory
* Tool Definitions
* Environment / Permissions
  → Assemble Model Input
  → Current Context
  → Model
  → Output**

其中：

**Output → Text Response**

或者：

**Output → Tool Call**

# A03｜Agent如何执行动作

## 核心问题

**当模型产生Tool Call以后，一个Agent怎样真正执行动作？**

## 重点要求

需要明确区分：

**模型产生动作请求**

和

**外部系统真正执行动作**

模型本身不直接进入电脑、数据库、文件系统或业务系统进行操作。

模型产生：

**Tool Call**

之后，需要由模型之外的系统负责实际执行。

## 核心流程

**Model
→ Tool Call
→ Harness
→ Tool / Runtime
→ Execution
→ Tool Result
→ Harness
→ Next Context
→ Model**

如果模型还需要更多操作：

**Model → Next Tool Call**

然后再次执行。

如果已经取得足够结果：

**Model → Final Answer**

因此，一个Agent任务可能包含多轮：

**Model → Tool → Result → Model**

形成Agent Loop。

---

## Harness需要表达的内容

Harness负责连接模型与真实执行环境。

需要表达它负责：

* 接收模型产生的Tool Call
* 判断可以使用哪些Tool
* 管理Runtime / Environment
* 处理相关权限
* 调用真正的执行系统
* 接收Tool Result
* 将结果重新加入下一轮模型输入
* 再次调用模型

---

## Runtime / Environment需要表达的内容

实际执行是否成功，还受到运行环境影响。

包括：

* Tool是否存在
* Working Directory是否正确
* Dependency是否满足
* Network是否可用
* Permission是否允许
* 外部服务是否正常
* 实际执行是否成功

需要表达：

**模型知道应该做什么，不等于当前环境一定能够执行。**

---

## Tool Result需要表达的内容

需要明确：

**Tool Call不是Tool Result。**

Tool Call只是模型提出的请求。

只有工具实际运行以后，才可能产生：

**Execution Status**

以及：

**Tool Result**

Tool Result返回以后，需要进入下一轮模型输入，模型才能根据真实执行结果继续判断。

---

## Agent Loop需要表达的内容

一次用户任务可能包含多轮：

**Model
→ Tool Call
→ Execution
→ Tool Result
→ Context
→ Model
→ Tool Call
→ Execution
→ Result
→ ……**

直到任务能够结束。

需要让用户理解：

**一次用户输入，不一定只对应一次模型调用。**

---

## 失败情况

A03需要能够表达：

Tool Call虽然正确，但实际执行仍可能失败。

典型原因包括：

* Permission Denied
* Dependency Missing
* Wrong Environment
* Tool Unavailable
* Network Failure
* Execution Error

失败结果同样需要返回给模型。

模型根据失败信息决定下一步，而不是把任务直接描述为已经完成。

---

## Verification

Agent执行完成以后，还需要表达最后一个阶段：

**Verification**

需要区分：

**模型说“完成了”**

与：

**任务已经被验证完成**

验证可能包括：

* 文件是否真实生成
* 文件是否可以打开
* 测试是否实际运行
* 测试是否通过
* 数据是否来自指定来源
* Tool Result是否真正支持最终结论
* 操作是否符合任务约束
* 是否仍然存在未确认事项

最终关系：

**Done ≠ Verified Complete**

只有完成必要验证以后，才能进入：

**Verified Complete**

|---|---|---|

|---|---|---|
| 0–12 秒 | 动作请求 | 简短交代摘要任务。读取请求从模型离开，停在 Harness，文件仍关闭。 |
